# ADR-0042: 400 行红线债务清偿 —— D11 的"另行开轮"到期

- **状态**: Accepted
- **日期**: 2026-09-18
- **决策范围**: anaphase-helix（`session_events.rs` → `session_events/`，`run_cycle.rs` → `run_cycle/`）
- **关联**: `ADR-0038` D11（本次不做：不解耦 400 行红线既有违规）· `ADR-0041`（周期身份，其代码落在 `session_events.rs`）· DNA 红线「代码超 400 行必须解耦」

---

## 一、背景：被推迟的债务，以及它没有被"不扩大"

`ADR-0038` D11 原文：

> **不解耦 400 行红线既有违规**——`run_cycle.rs`、`session_events.rs` 均已超 DNA 红线，属**既有技术债**；本轮只加入必要的最小代码，**不扩大**，**另行开轮**。

**实测（2026-09-18）**：

| 文件 | 行数 | 相对 400 |
|---|---|---|
| `run_cycle.rs` | **2093** | 5.2× |
| `session_events.rs` | **1545** | 3.9× |
| `main.rs` | 1171 | 2.9× |
| `contract/mod.rs` | 703 | 1.8× |
| `adapters/http_reasoning.rs` | 540 | 1.35× |
| `rails.rs` | 488 | 1.2× |
| `adapters/mind.rs` | 474 | 1.19× |

**⇒ D11 的两个条件都没被满足**：既没有"不扩大"（`session_events.rs` 在本轮的身份改动中又长了约 250 行），"另行开轮"也一直没有发生。

**⇒ 本 ADR 是那"另行开轮"。**

---

## 二、决策

### D1：清偿顺序——先 `session_events.rs`，再 `run_cycle.rs`

- **先拆 `session_events.rs`**：它在本轮被改动最多，契约（身份 vs 重放句柄）刚刚稳定、测试 284 全绿 ⇒ **回归网最密**，是最安全的窗口。
- **`run_cycle.rs` 随后拆**，方式见 D2。
- **两者都拆完，才继续 B18**（身份传播到 Tuck）—— 否则 B18 要在 1545 行里找位置，且会再扩大一次。

### D2：拆分方式——沿用仓内既有目录式模块，不发明新结构

仓内已有 8 个目录式模块（`adapters/` / `contract/` / `pipeline/` / `ledger/` / `evidence/` / `criteria/` / `ci144/` / `bin/`），均以 `mod.rs` 为入口。本次沿用。

**`session_events.rs` → `session_events/`**

| 文件 | 承接 |
|---|---|
| `mod.rs` | 重导出 + `EventType` + `SessionEvent`（对外契约类型） |
| `identity.rs` | `job_digest` / `try_allocate_period_id` / `allocate_period_id` / `is_period_id` / `is_job_id` / `PeriodRef` / `Resolved` / `resolve_period` / `resolve_one` |
| `stream.rs` | `SessionEventStream`（开流 / `emit` / redact / `emit_period_start`） |
| `query.rs` | `list_periods` / `read_period` / `read_summary` / `PeriodSummary` |
| `naming.rs` | `rename_period` / `period_name` / `freeze_name`（`.name` sidecar） |
| `crystallize.rs` | `crystallize` / `CrystalSuggestion` |

**`run_cycle.rs` → `run_cycle/`**：按 `HelixState` 状态机分段，`mod.rs` 只留 `AgentLoop` 与调度。
**⇒ 注意**：反射那一段**不得**命名 `reflex.rs`——`src/reflex.rs` 已存在（`ReflexArc`）；用 `reflex_check.rs`。

### D3：验收判据（可证伪）

1. **没有任何源文件 > 400 行**（含 `mod.rs`）—— 命令：`find src -name '*.rs' -exec wc -l {} + | sort -rn | head`
2. **纯移动**：拆分前后**公开 API 不变**（类型名、函数签名、可见性），除非一并记录为独立决定。
3. **测试数不变**：拆分不得删改测试（277→284 那条基线只增不减）。
4. **`cargo test` 全绿**（当前 284/0）。
5. **无死代码**：拆分后不得留下未被引用的 `pub` 重导出或空模块。

### D4：本 ADR 不清偿的（诚实边界）

- `main.rs`（1171）、`contract/mod.rs`（703）、`adapters/http_reasoning.rs`（540）、`rails.rs`（488）、`adapters/mind.rs`（474）**仍超线**。
  **⇒ 本 ADR 只清偿被 D11 点名的两个文件**；其余另行开轮，**不得因为"拆过一轮"就宣称红线清零**。

## 三、影响

### 正面
- 本轮改动最多、契约刚稳定的两个文件获得结构性边界，后续改动（B18/B17）不再往单体里塞。
- 身份逻辑（`identity.rs`）从 1545 行里独立出来 ⇒ **"唯一正确性前提"变得可单独审查**（K-031 的教训）。

### 代价与风险
- **大 diff**：纯移动仍会产生一次数百行的 diff，审查成本高 ⇒ 必须**分段提交**（一个模块一次），且**每段跑一次全量测试**。
- **重导出层可能掩盖耦合**：若 `mod.rs` 变成"什么都转发"的出口，则只是把单体换成了目录。**⇒ 判据 5 就是为此设的。**
- **`use` 路径变动会波及 `main.rs` 与测试**：预期 `pub use` 保持外部路径不变，如不可行则记录为独立决定。

---

## 四、不解决什么

- **不改变任何行为**。本 ADR 是结构决定，不含语义决定；语义若有变动，必须另立 ADR 或写进对应坑记录。
- **不偿还其余 5 个超线文件**（见 D4）。
- **不为"行数"而拆**：拆分边界按**职责**划，不按行数切齐。若某职责拆完仍超 400，**如实记录并说明**，不用硬切制造假达标。

*一个文件长到 2000 行时，读它的人已经不再是在读一个模块，而是在读一个目录的目录。*

## 五、拆分额度与窗口（2026-09-18 追加，**实测后写入**）

### D5：纯移动拆分**不可能零增量**——已实测，故授权一次性额度

**实测**（在 worktree 上真拆 `src/criteria/mod.rs`）：

```
拆分前  src/criteria/ = 291 NOCL
拆成 3 个文件后        = 295 NOCL      ⇒ +4（+1.4%）
```

**原因**：`mod.rs` 新增 `pub use part_a::*;` 等**原文件里不存在的行** ⇒ **这部分增量是永久的**，不是窗口期现象。其余是每个新文件的模块头与 `use`。

**⇒ 后果**：目录级 ratchet 会在**拆分第一天**变红，而红的理由是"检查器在正常工作"。
**⇒ 两种错误处置**：把 ratchet 改成 report-only、或临时豁免 —— **两者都在教"重构＝关闸门"**，而那正是被跳过的门禁（§1.6 同族）。

**⇒ 采用**：**提前授权一个有数、有理由、有期限的额度**（`ci/baseline.toml` 的 `[[split_window]]`）：

```toml
[[split_window]]
target    = "src/"
allowance = 60          # 估自一次实测（约 +6/文件 × 7 段，向上取整）
reason    = "ADR-0042 run_cycle.rs 纯移动拆分：re-export 面 + 每文件模块头"
due       = "2026-10-09"
```

**三条语义（已实测）**：
1. **额度只放开目录聚合，不放开单文件增长** —— 额度内目录级放行，**文件级 ratchet 仍然红**（实测：给 `trace.rs` 加 30 行 ⇒ 目录放行、文件红）；
2. **超额仍红**（实测：加 70 行 > 60 ⇒ `src/ 5004 -> 5074 (with a +60 split allowance)`）；
3. **窗口内目录基准不写回**（否则额度会被逐次吃掉），**窗口关闭后重新播种**。

### D6：新文件"一出生钉死"的例外

新文件首次出现即被播种为当前值。**但在拆分窗口内拆出来的文件，第二天就要补模块头与 re-export** ⇒ **这个窗口内允许新文件按同一额度上调一次，窗口到期后一律钉死。**

**⇒ 判据**：窗口到期后，**任何新文件的第一条 ratchet 值等于它出生时的值**，此后只减不增。

### D7：本 ADR 的额度**不是豁免**

豁免是"允许违规"（人签、带 owner、只减不增）；**额度是"承认重构会改总量"**（脚本可验证、有上限、到期自动失效）。
**⇒ 两者分开存放**：豁免在 `baseline.toml`（人签），ratchet 基准在 `ratchet.gen.toml`（脚本写）；`split_window` 属前者但**不是豁免类条目**，因为它带的是**上限**而不是"允许超线"。

### D8：第三类额度 `fix_window`——**修复不是债，也不是重构**

**触发**：B22（僵局的通知不得依赖面板）与其前置 K-035（模型声明的 impasse 被状态机抹掉）
的实现让 ratchet 变红。而 ratchet 是 `min(old, current)`，**不可能上调基准**
⇒ 合法增长只有 `[[waiver]]` 与 `[[split_window]]` 两个出口，**两个都不对**：

| 出口 | 语义 | 承诺 |
|---|---|---|
| `[[waiver]]` | **债** ——「我会还」 | owner + due |
| `[[split_window]]` | **重构额度** ——「结构变了」 | cap + ADR |
| **`[[fix_window]]`** | **修复** ——「它本来就该存在」 | **cap + K-ID** |

**⇒ 记成 waiver 等于宣布"修复是债务"**：它会到期、会被催还，而**修复是资产增加**。
**⇒ 并入拆分额度则毁掉 `估 60 / 实 X`** —— 那是留给「为什么要拆 2093 行」的唯一答案。

**三条语义（与另两类对称，均已实现并测试）**：
1. **不带 `due`**：修复不会在某天自行消失。**带 `due` 的 fix_window 是错误**，检查器返回 **exit 3** 拒绝。
2. **必须带 `k_id`**：合法性来自坑记录（「变更须引坑 ID」这条规则用到行数上）。缺 `k_id` 同样 exit 3 拒绝。
3. **可放开单文件**（与 `split_window` 相反），**且只绑指名目标**，不摊给邻近文件。

**⇒ waiver 只降不升**：一个被反复上调的 waiver 事实上就是手写基准。
要上升，走 `fix_window`；waiver 的数值（即 ratchet 基准）只由脚本按 `min()` 写。

**⇒ 实测基准（2026-09-18）**：`src/run_cycle/` 1156→1275（cap 119）、
`src/run_cycle/mod.rs` 1142→1155（cap 13）、`src/main.rs` 936→940（cap 4）。
**拆分额度 `src/ allowance=60` 原样未动**，两者分开记账。

**⚠️ 同批登记的一个未决项**：新文件按 D6 出生播种 ⇒ 单文件放行，**但仍计入目录总额**
⇒ 新文件会吃掉目录额度，而**新建文件恰是"新增观测"的正常手段**。

**⇒ 2026-09-18 裁定方向（审查第 29 轮）：纯出生播种不做，纯钉死也不做，取折中。**

| 方案 | 问题 |
|---|---|
| 新目录出生即播种（与 D6 对称） | **它从第一天起就有自己的额度**，而那正是 D6 之前那个洞。目录级 ratchet 的唯一作用是防"**拆文件**"变成"**新增总量**" |
| 新目录钉死在出生值 | 等于**禁止它成长** —— 一个新建目录永远不能加文件 |
| **折中（采纳，未实现）** | **播种值 = `min(所有子文件出生值之和)`**；**不允许单独上调，只允许随子文件一起下降** |

**⇒ 折中的性质**：**有上界**（= 子和，不是无限额度），**且非禁锢**（随子文件下降而下降）。

**⇒ 落地判据（实现时必须同时给出）**：把 `min(子和)` 换成 `max(子和)` 或 `∞` ⇒ **必须有测试变红**。
**⇒ 状态：未实现。**

### D10：拆分优先级按 **churn** 排，不按行数排（2026-09-18，**实测后追加**）

**触发**：第 37 轮审查改用实证结论 —— **行数与缺陷密度相关性很弱**，
更有预测力的是 **变更频率（churn）** 与"被多少 commit 碰过"。
**⇒ 本 ADR 的 waiver 名单是按行数排的，所以拿本仓 git 历史验一遍。**

**实测**（`git log --format= --name-only -200`）：

| 文件 | churn | NCLOC | 本 ADR 原名单 |
|---|---|---|---|
| `src/main.rs` | **46** | 943 | ✅ |
| `src/run_cycle.rs`（拆分前） | 35 | — | — |
| **`src/config.rs`** | **27** | — | ❌ **不在名单** |
| `src/session_events.rs`（拆分前） | 20 | — | ❌ |
| `src/lib.rs` | 19 | — | ❌ |
| `src/adapters/mod.rs` | 18 | — | ❌ |
| **`src/bind.rs`** | **1** | 302 | ✅ |
| **`src/rails.rs`** | **2** | 370 | ✅ |

**⇒ 数据说**：**全仓 churn 最低的两个文件（`bind.rs` 1、`rails.rs` 2）排在拆分名单上，
而 churn 27 的 `config.rs` 不在名单上。**

**⇒ 优先级修订**：
1. **排序依据 = churn**；**行数只作硬阈值判据，不作排序依据**；
2. **`main.rs` 从"最后"改为"最前"** —— 它 churn 第一（46）**且**最大（943）。
   **这推翻第 31 轮 🟠2 的建议**（该建议说 run_cycle 四段拆完后 main.rs 优先于其余）；
3. **`bind.rs` / `rails.rs` 降级** —— 它们只因行数超标在名单上，而事实上几乎无人改动；
4. **"按 `HelixState` 拆"的依据不变**（5 个改变的理由 = 单一职责）—— **换的只是顺序**。

**⇒ 判据（可重跑）**：
```bash
git log --format= --name-only -200 | grep -E '^src/.*\.rs$' | sort | uniq -c | sort -rn
```
**⇒ 未知/未声明范围仍是缺陷**：churn 只统计了**近 200 个提交**；
该窗口必须随使用一起声明，否则它就是一个未声明范围的数。

### D11：收益判据改为**模块边数下降**，并记实测基线（2026-09-18）

**触发**：第 42 轮实证审查 —— **本 ADR 的收尾指标测错了东西**。
原文记的是「段数 / 缺陷数 / 修复行数」，**三者全是规模与成本，没有一个测收益**。
Kim et al.（FSE 2012）的实地结论是：**被重构模块在模块间依赖数与发布后缺陷上显著下降**。
⇒ **正当性只能来自"依赖下降"或"解锁某个能力"，不能来自"文件变小了"。**

**⚠️ 一处工具核对（审查的处方不成立）**：审查建议"用 `cargo metadata` 导出依赖边数"。
**实测：`cargo metadata` 给的是 crate 级依赖**（本包 23 条，均为 `axum`/`chrono`/…），
**拆分一个模块完全不会改变它** ⇒ **它测不到本 ADR 关心的东西**。
模块边只能扫源码里的 `crate::X` 引用。

**⇒ 实测基线（拆分前，`crate::X` 引用去重计数）**：

| 文件 | 模块边 | NCLOC |
|---|---|---|
| `src/main.rs` | **1**（`config`） | 943 |
| `src/config.rs` | **1**（`judge`） | ~350 |
| `src/run_cycle/mod.rs` | **16** | 1146 |

**⇒ 数据推翻了"先拆 main.rs 能降依赖"这个想法**：它已经只有 1 条边，
**拆它不会降低模块耦合** —— 它的正当性只能是**解锁一个能力**（一个更好的落点），
**而那正是前一轮的论证**。反之 `run_cycle/mod.rs` 的 16 条边是**结构性**的，
**它剩余 4 段的拆分有最硬的依赖下降理由**。

**⇒ 判据（每段拆分必须执行）**：
1. 记**拆前 / 拆后**的模块边数，**断言下降**（或说明为何不降，如"解耦收益在别处"）；
2. `fmt` / `clippy` 的采纳**不得在拆分进行中做**（会污染 churn 与 blame）—— 见 `.git-blame-ignore-revs`。

**⇒ 同时记一条反向证据（审查提供）**：Koru 发现规模-缺陷关系是对数形，
小模块**按行更成问题** ⇒ `bind.rs`(302) / `rails.rs`(370) **可降级，不可免检**。

### D12：D11 的"断言边数下降"**被自己的数据推翻**，并给出可用判据（2026-09-18）

**D11 说**：每段拆分记拆前/拆后模块边数，**断言下降**。
**⇒ 按要求先校准，不自作主张**：拿**已经完成**的 `session_events` 拆分（`3e92a72`）当样本，
在 `3e92a72^` 建 worktree，用同一个扫描器量两侧。

| 口径 | 拆前 | 拆后 | 方向 |
|---|---|---|---|
| **边总数** | 44 | 65 | **+48% ↑ 上升** |
| **单文件最大 fan-out** | 15（`run_cycle.rs`） | 16（`run_cycle/mod.rs`） | **↑ 未下降** |
| 文件数 | 32 | 48 | ↑ |

**⇒ 两个候选口径都不成立。** 边总数上升（每份各自 `use`），
而最大 fan-out 未降 —— 因为被拆的 `session_events.rs` 本来只有 2 条出边，
**它不是 fan-out 最高的文件**。

**⇒ 所以"断言边数下降"撤回。** 且**我不再换一个没校准过的断言上去** ——
那正是本项目反复犯的同一个错（用未验证的判据替代被推翻的判据）。

**⇒ 一个不舒服但必须记下的结论**：
**本项目唯一已完成的拆分，用任何一个可用口径都测不出耦合收益。**
它的正当性是"1545 行拆成 5 个模块"，**即规模** ——
而第 42 轮引的实证（Ferreira/Kim）说：**规模下降不是正当性**。
**⇒ 这条对 `session_events` 是追认不了的；它只能作为"以后不许再用这个理由"的先例。**

### 可用的判据（实测，二选一）

**① fan-in + SDP（静态、当下可测，且 `config.rs` 已经违规）**

Robert C. Martin 的稳定依赖原则：**不稳定性 I = fan-out / (fan-in + fan-out)**；
**被大量依赖的模块应当稳定**。

**实测（`crate::X` 引用去重计数）**：

| 模块 | **fan-in** |
|---|---|
| **`config`** | **11** ← 全仓最高 |
| `adapters` | 7 |
| `ledger` | 5 |
| `contract` / `trace` | 4 |

`config.rs`：fan-in 11、fan-out 1 ⇒ **I = 1/12 = 0.083（极稳定）—— 而它被改 27 次。**
**⇒ 高 fan-in + 高变更 = 明确违反 SDP。这是本项目第一个"当下就测得出违规"的拆分理由。**

**⇒ 且它给出了"特性自持配置"的可测判据：降低 `config.rs` 的 fan-in。**
不是"它变小了"，是"**依赖它的模块变少了**"。

**② 变更耦合（co-change，只能向前测）**
拆分的收益若在"改动不再需要横跨多个模块"，那它**只能在拆分之后用 git 历史测**。
`session_events` 今天才拆，**现在没有拆后历史 ⇒ 不可校准**。
⇒ 登记为**向前可测**，不作为当前判据。

**⇒ 判据优先级（采纳第 42 轮）：耦合决定"拆不拆、怎么切"；churn 只在耦合相当的候选之间决定"先拆谁"。**
**⇒ 按此，当前唯一有实测违规证据的目标是 `config.rs`（fan-in 11 / I=0.083 / churn 27），

### D14：接口变更的正确模式是 Parallel Change（`config.rs` step B）

**问题**：`config.rs` 的"特性自持配置"要让 fan-in 从 11 降下来。
**⇒ 而"降 fan-in"在逻辑上就等价于"改接口"** —— fan-in 就是"多少模块引用它"，
要它下降就必须让那些模块不再引用它 ⇒ 必须改调用点。**所以它不是纯移动，快照证明不了行为保持。**

**⇒ 采用 Parallel Change（Fowler, 2014：expand → migrate → contract）+ Delegation**：

| 阶段 | 动作 | 可验证吗 |
|---|---|---|
| **expand** | 各模块声明自己的配置；`config.rs` 保留字段但**委托**到新位置 | ✅ 行为保持，快照可验 |
| **migrate** | 11 个调用点**逐个**迁移 | ✅ 每步小、可验 |
| **contract** | 删 `config.rs` 里的旧字段 | ✅ **此时 fan-in 才真正下降** |

**⇒ 关键**：**fan-in 下降是 `contract` 阶段的验收判据，不是每一步的门禁。**
我把它当成每步的门禁，它当然在第一段就失败 —— 这解释了我为什么觉得"没法验证"。

**⇒ 且 Rust 在这里有别人没有的优势**：改字段/签名 ⇒ **编译错误 ⇒ 编译器免费给出穷尽的调用点清单**。
rustc 的穷尽性检查与类型系统是**机械的**，不靠 grep。**⇒ 接口变更在 Rust 里的风险低于直觉估计。**

### D17：行数不是复杂度的代理 —— 采用三层信号，400 保留为分层边界（2026-09-20，**实测后写入**）

**被审查的提案**：以「认知复杂度 / 行数 / 重复率 / churn」多维指标**替代** 400 行红线，把 400 **降级为 warning**。

**裁定：方向吸收（LOC 不是复杂度的好代理）；机制诊断驳回；「撤掉 400」驳回。**

#### D17.1 决定性实测（命令可复现）

`clippy::cognitive_complexity` 在 `src/` 内命中 **9 个函数**（下表 NCLOC 由 `ci/check_line_budget.py` 的计数器量得）：

|---|---|---|---|
| **86** | `arm_reflection` | 215 | **过闸** |
| **82** | `arm_reasoning` | 229 | **过闸** |
| 79 | `execute_current_state` | 653 | 超限 |
| 55 | `arm_memory_retrieval` | 81 | **过闸** |

**⇒ 9 个里 4 个住在 400 闸门判为「合格」的文件里；全仓最难懂的两个（CC 86 / 82）所在文件连 230 行都不到。**

`clippy::too_many_lines`（阈值 100）另有 **10 处**，最大为 `src/main.rs:13` 的 **505 行**。
同批还抓到 `too_many_arguments` **8/7**（`src/bin/up.rs` 的 `menu_loop`）—— 这是**接口耦合**，第三个维度。

#### D17.2 为什么「LOC ≠ 复杂度」这一条必须吸收

**400 行回答的是导航问题**（我能不能找到东西）；**CC 回答的是理解问题**（这段东西难不难懂）。
本 ADR 此前把两者当成一件事 —— **这是本 ADR 的一个错误，由本轮数据更正。**

#### D17.3 但机制不是提案说的那个（实测反驳）

提案称「强行 400 行会造成耦合扩散 + 公共代码重复」。本仓实测**没有发生**：四次拆分是**编译器验证过的纯移动**，无重复代码，耦合下降（CBO 基线见 D11–D13）。

**并且本 ADR 需更正自己此前的表述**（若说过「同一函数拆前拆后 CC 不变」）：**拆前它根本不是函数。**

```
拆分前：execute_current_state()  第 785–1291 行  NCLOC=390
         └ 其中 Reflection 分支  第 1000–1289 行  NCLOC=209（匿名内联分支）
拆分后：arm_reflection()          NCLOC=210   CC=86   文件 215（过闸）
```

**⇒ 400 行是「发现与结构化」机制，不是「复杂度」机制。** 它把匿名的内联复杂度变成有名字、可指认、可单独测试的函数，然后**停下** —— 因为「这个函数是不是太难懂」需要另一把尺。
**⇒ 是这把闸门让 CC 86 第一次变得可见。** 这也是它不该被撤掉的理由之一。

#### D17.4 为什么驳回「把 400 降级为 warning」

1. **提案自己的论据（函数级是更好的信号）是「加一维」的理由，不是「撤一维」的理由。**
2. **门禁正在产出结果**：`over_total` 已由 **1365 降至 1090**（门禁口径，5 个文件）。在它开始见效时关掉它，是拿一个有效机制去赔一个错配的机制。
3. **400 行真正的伤害已经处置完毕，且伤害不在这个数字上**：伤害在**执法装置** —— 六个 allowance 类 + 重取窗口 + 换类。`floor = 5` 是**猜的**（实测修复 Q1 = 36，**14 倍偏差**），一次会话内被绕过三次。已处置：floor 重标定为实测 **36**、**重取通道退役**、文件计数换成 `over_total`（D16）。
   **⇒「不科学的 400 行」中不科学的那部分已经拆掉了；剩下的 400 服务的是另一个目的。**

#### D17.5 工具与阈值

- **不引入 SonarQube / radon / pylint**：语言生态不符，且本机离线不可得。
- **Rust 等价物已在编译器工具链内**，零新增依赖、零网络。
- **阈值不自造**：上表 clippy 自报的 `(46/25)`、`(104/100)` 的分母 **25 / 100 即 clippy 默认值**（本地实测观测所得，非外部引用）。本仓 CC 分布为 n=9、min 28、中位 46、max 86，与 25 之间有**干净间隔**，不会神经质抖动。
  **⇒ 采用工具默认，不自造数字** —— 本 ADR 已因自造 `floor=5` 被绕过三次。
- **范围必须复用 `iter_sources` + `is_test_path`**：同一批 lint 会把 `target/debug/build/.../out/helix_mind.rs` 抓成 **610 行**、`tentacle.v1.rs` 抓成 **202 行**。生成代码的噪声会盖过信号。**任何新检查器都得走同一个 scope 函数**，否则口径会再次分叉（同 D16 末尾的警告）。

**⚠️ 顺带更正一个已记录的数字**：本 ADR 此前记 `over_total = 1082`，**本轮门禁口径实测为 1090**（`run_cycle/mod.rs` 645 → 653，H5/H2b 落实所致）。
**⇒ 重申规则：任何写死的数字都必须带获取命令**，否则它会像 343 一样过期。
